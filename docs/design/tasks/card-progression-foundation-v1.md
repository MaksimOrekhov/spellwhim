# Черновик задачи: Card Progression Foundation v1

**Статус: DRAFT / PLANNED, реализация не начата.** Основа — [GDD v2.0](../spellwhim-gdd-v2.md), особенно §3–6/17, и [Roadmap, этап 1](../spellwhim-gdd-v2-roadmap.md). Сначала подтвердить продуктовую границу сейва и требуемые будущие операции; значения улучшений и золота этой задачей не утверждаются.

## Цель

Создать надёжную основу развития колоды: конкретные постоянные копии, выбор/пропуск награды с просмотром колоды, атомарные операции удаления/замены, представимость одного улучшения и базовое сохранение существующего похода. После перезапуска возвращаются те же копии/владельцы/предложения. Числа боя, старт 18/8 и нынешняя карта остаются контрольной системой.

Не требуется заранее выбрать файлы, классы, функции или библиотеку хранения. Исполнитель изучает текущий поток состояния и предлагает минимальную модель, сохраняющую инварианты. Логические поля GDD — контракт данных, а не требование скопировать псевдотипы.

## Системы, которые необходимо изучить

| Текущая часть | Что важно для задачи |
|---|---|
| `types.ts`: CardDefinition / CardInstance | Определение общее; нынешний instanceId относится к конкретному бою, постоянного состояния улучшения нет |
| `campaign.ts`: DungeonRunState.deck / claim / carriedHeroes | Сейчас массив CardId, одиночный pendingReward; операции создают новые состояния, seed наград независим |
| `battle.ts`, `deck.ts`, preview | Копии расходятся по hand/draw/discard/exhausted/pending; карта не добирает себя; actionId идемпотентен |
| `useBattle.ts`, `App.vue` | Есть и ownedDeck, и состояние похода; определить единственный авторитет постоянной колоды, исключить рассинхронизацию |
| Награды, рука, карточный display | Стабильные Vue-ключи по экземплярам, просмотр всей колоды, выбор одной из нескольких одинаковых копий |
| Предметы/герои | ownerInstanceId должен остаться связан с тем же участником после reload и нового боя |
| Балансные лаборатории/fixtures | Старые CardId-колоды и контрольные traces должны продолжать работать, данные не перезаписываются |

Это список точек исследования, не предписание, что все перечисленные файлы обязательно редактировать.

## Функциональные требования

### F1. Постоянные копии

- Каждая стартовая/полученная карта различима на протяжении похода. Две копии одного определения имеют разные стабильные ID.
- Модель способна представить upgrade 0/1. В активной игре этого этапа новые улучшения **не выдаются и не меняют эффекты**, пока каталог/канонический resolver не введены этапом 2.
- Розыгрыш, сброс, добор и выбывание до конца боя не уничтожают постоянную копию. Победа возвращает постоянный состав независимо от её последней зоны.
- Новый поход создаёт новое пространство ID; повторная загрузка продолжает сохранённые счётчики. Restart/новый бой не допускают коллизий анимационных actionId или старых callbacks.
- Наследуемые `CardId[]` остаются поддержанным входом лабораторий либо имеют явный совместимый адаптер. В переходном слое нельзя дважды создать карту из одного приобретения.

### F2. Награда и обзор

- После обычной победы можно взять одну из прежних трёх карт или пропустить без компенсации. Перечень/статистика определений не меняются.
- Просмотр колоды доступен на экране выбора: имя, класс, стоимость, число копий, состояние каждого экземпляра; закрытие возвращает к тому же offer, не запускает его заново.
- Принятие/пропуск однократны. Повтор события/клика/восстановления не выдаёт вторую карту и не пропускает следующий узел.
- Для нынешней элиты сохраняется **существующая** экономика «карта или предмет». Два новых трека R2 ещё не вводятся; модель сейва должна иметь понятный путь расширения, но не требует преждевременного переписывания награды.

### F3. Операции развития

- Удаление: по стабильному ID убрать одну копию; ошибка/отсутствующий ID не меняют состояние.
- Замена: предложение зафиксировано, убрать один выбранный ID и создать новый; размер прежний, не переносить улучшение автоматически, всё или ничего.
- Операции вызываются между боями через проверяемый интерфейс/сценарный стенд; новые кузницы/фиктивные узлы и новый генератор не нужны для проверки основы.
- Иметь контракт однократного улучшения 0→1 и его сохранения, но фактические варианты/эффекты приходят следующей задачей. Тестовый каталог допустим в изолированных тестах; нельзя показывать игроку улучшение с выдуманным эффектом или принимать неразрешённый вариант в обычный бой.
- Закрытый/уже разрешённый источник операции не может повторно выдать услугу. Отмена до подтверждения не потребляет источник. После подтверждения reload не возвращает его неиспользованным.
- Золотых карт сейчас нет: подготовить место для общей проверки уникальности при выборе/замене, не расширять игровой каталог фиктивными золотыми ID. Реальные ограничения золота активируются вместе с каталогом в этапе 4.

### F4. Базовый сейв

Логически сохраняются:

- run ID, seed, версия схемы/правил/генератора/каталога, конфигурация;
- готовая карта со скрытым зафиксированным контентом, текущий/посещённые/завершённые узлы, статус;
- герои с постоянными ID, HP/maxHP, предметы и их владельцы;
- копии колоды, их состояния и счётчики создания;
- незавершённое предложение и уже разрешённый выбор, ID операции;
- entry snapshot текущего боя для повторного старта при закрытии во время боя;
- расширяемые результаты событий/будущие эффекты по известной схеме; до соответствующих механик пусты, неизвестные исполняемые эффекты не загружаются молча.

Сохранение после создания, перед входом в бой, после его завершения вместе с предложением, после принятия/пропуска/предмета/привала и при завершении похода. Переход результата и приобретение нельзя сохранить в несовместимых половинах.

**Предлагаемая граница восстановления:** незавершённая награда возобновляется точно; бой — с начала того же боя по сохранённому entry snapshot и seed. Не сохранять partially paid pending как завершённый межкомнатный результат. Не выдавать проигранную/победную награду из незавершённой анимации. Если нужна точная середина боя, сначала согласовать больший объём, не обещать его базовым snapshot.

Хранилище выбирает исполнитель с учётом браузера/Tauri. JSON-контракт должен отделяться от транспорта; не добавлять тяжёлую зависимость без необходимости. IndexedDB предпочтителен при транзакционной модели; localStorage допустим для первого небольшого snapshot при атомарной записи/предыдущем поколении, проверке ошибок и понятной совместимости. Автоматический выбор рабочей копии из повреждённых записей проверяется, не предполагается.

### F5. Неисправные и старые сохранения

- Проверить схему, версии, допустимые ID, диапазоны здоровья/улучшения, уникальность копий/владельцев, положение на карте и состояние offer до публикации в UI.
- На несовместимом каталоге не выкидывать неизвестную карту, не лечить героя «по умолчанию» и не строить новую карту из того же seed.
- Миграция детерминирована и тестируется на объявленных поддержанных версиях; хранится backup исходного сохранения. Не обещать вечную совместимость любых будущих правил.
- Ошибки доступа/quota/повреждения не должны молча терять прогресс. Показать отсутствие надёжного сохранения и предложить retry/экспорт доступного snapshot. Повтор retry использует тот же ID операции.
- В игре до этого этапа нет установленного формата сейва: миграцию несуществующего «старого сейва v0» не изобретать. Совместимость с текущими API/контролями и последующие migration-fixtures всё равно обязательна.

## Критические инварианты

1. Постоянная колода — единственный авторитет состава; UI и боевой адаптер не изменяют независимые копии списка отдельно.
2. Получение +1, пропуск 0, удаление −1, замена 0, улучшение 0 по размеру. Дубли определений не являются дублями экземпляра.
3. Каждая постоянная копия имеет ровно одно соответствие в активном бою; она одновременно не находится в двух зонах. Карта pending не считается потерянной и не копируется в сброс дважды.
4. Никакого улучшения общего CardDefinition. Приёмку legacy battle fixtures выполнять на тех же прежних эффектах.
5. Мана/HP/result изменяются только каноническими операциями. Пропуск награды не лечит и не сбрасывает seed.
6. Артефактов не больше двух, по одному на участника; владелец существует после reload. Триггеры боя заново инициализируются только в новом бою.
7. Операции выбора/сервиса/перехода однократны по источнику/ID. Предложение не регенерируется от просмотра колоды, отмены, смены вкладки и загрузки.
8. Невалидная операция/сейв не публикуются как частично корректный поход. При доступном backup восстанавливается целостное предыдущее состояние.
9. После смерти/финала нельзя продолжить бой/сервис через устаревший callback. События анимации коррелируются с текущим поколением/действием как прежде.
10. Скрытые встречи/подготовленный размер не попадают в публичные модели и решения ботов в ходе интеграции сохранённой карты.

## Тесты и ручная проверка

- Две одинаковые карты: удалить/заменить/изолированно сохранить улучшение одной, другая неизменна; все ID устойчивы через два боя/перемешивание/restart.
- Все зоны: pending→resolve, stale/repeated actionId, exhaust→новый бой, draw при полной руке; ни одна копия не исчезает.
- Принять/пропустить награду дважды; reload перед выбором/после выбора/после победы до выбора; прежний offer и один итоговый результат.
- Нынешняя элита: выбрать карту либо предмет, заменить занятый слот с подтверждением; reload владельца и награды. Не появляется двойной приз.
- Сервисы в стенде: отказ, невалидный старый ID, неоднозначный class owner, исчерпанный offer, повтор source operation; отсутствие частичной замены.
- Сейв: round-trip поддержанных фаз, битые/лишние/неизвестные значения, обрезанный JSON, неизвестная версия, сбой записи, backup/retry. Логический hash состояния сравнивается без несущественных timestamp.
- Закрытие в середине боя/карточной анимации возвращает заявленный entry snapshot, а не новое случайное начало или частичное приобретение.
- Последовательности операций с generated фиксированными seed; минимум из E02. Исторический эталон 427 и исходный suite проходят **без перезаписи эталона**.
- Для изменений типов/Vue — `npm run build`; для правил/адаптеров — `npm test`. Ручной браузерный проход: 1280×720 и 1920×1080, награда/просмотр/пропуск/сохранение/reload/финал. Снять временные viewport overrides после проверки.

Проверять содержательные инварианты, не добавлять тесты, которые только повторяют внутренние имена/структуру выбранной реализации.

## Что не входит

Новый старт 14/8, баланс/эффекты улучшенных карт, золотые определения и новые предметы, R2, новая карта/комнаты/ростер, A/B/C лечения, события и их игровой UI, валюты/рюкзак/третий слот, новые герои, точный combat resume, сервер/облако/аккаунты. Не создавать видимые заглушки этих систем ради демонстрации foundation.

## Критерии приёмки

1. Существующий полный поход играется с прежними числами, но обычную награду можно пропустить и просмотреть колоду.
2. Постоянные копии и их состояния сохраняются; удаление/замена проверяемы на отдельных копиях, источник не расходуется дважды.
3. Закрытие/восстановление работает во всех заявленных границах, включая pending reward; ограничение входным snapshot боя явно описано.
4. Предложения, seed и владельцы совпадают после reload; повторы команд не дублируют награду.
5. Текущие тесты/сборка и новые содержательные проверки проходят, контрольные fixtures/прошлые исследования не переписаны.
6. Нет скрытых изменений стартовой колоды, HP/маны, карточных эффектов, врагов или количества узлов.
7. Есть краткое инженерное описание выбранного контракта/совместимости и известные ограничения; GDD/Roadmap помечают реализованное только после приёмки.

Результат этой задачи должен сделать последующий этап улучшений безопасным и обозримым. Он не должен заранее связывать исполнителя архитектурой, выбранной только по текстовому исследованию.
