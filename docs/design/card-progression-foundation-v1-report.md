# Card Progression Foundation v1 — технический отчёт

19.10.2026. Ветка `codex/card-progression-foundation-v1`, база — `origin/main` (`946f05460aa0bbec45e3108cf41779874e5a3935`), уже содержащая GDD v2.0.

## Реализованная граница

Постоянные копии, принятие/пропуск обычной награды, просмотр колоды в обычной и элитной награде, программные операции удаления/замены и контракт одного улучшения; локальный сейв существующего похода. Старт 18/8, экономика B, эффекты, здоровье, противники, семиузловой маршрут, арты и элитная экономика «карта или предмет» прежние. Все игровые предложения этого этапа имеют улучшение 0. Кузниц, новых комнат и реальных улучшенных эффектов нет.

## Постоянная колода и операции

`DungeonRunState.deck: PersistentCard[]` — единственный источник постоянного состава. Копия содержит `instanceId`, `definitionId`, `upgrade: 0 | 1`. Каждый новый поход получает UUID `runId`; последовательные ID `${runId}/card/N` и `nextCardId` сохраняются. Даже одинаковый seed нового похода не переиспользует экземпляры. Герои также имеют постоянные ID пространства похода; владельцы предметов ссылаются на них.

Бой получает отдельные объекты с теми же ID и уровнем. Все зоны, включая pending/exhausted, остаются боевыми: их перемещения не редактируют колоду похода. Следующий бой снова создаётся из полного постоянного состава. `createBattle`/`createCampaignBattle` принимают также старый `CardId[]`; его порядок, RNG и прежние боевые ID не изменены. Линейные лаборатории сохраняют старые функции наград. В приложении `useBattle({ runDeck: () => run.value.deck })` читает поход; локальное добавление карты этим адаптером запрещено. Его старый standalone-режим нужен существующим тестам/лабораториям.

| Операция | Результат / однократность |
|---|---|
| `claimDungeonReward` | +1 копия; уровень берётся из зафиксированного `offer.cards`, счётчик +1 |
| `skipDungeonReward` | 0 копий, без компенсации; только обычная награда |
| `claimDungeonArtifact` | Прежний личный слот/подтверждённая замена; карточный приз закрывается вместе с предложением |
| `offerDeckOperation` | Один фиксированный источник `sourceId` с вариантами замены; повторная регистрация отвергается |
| `confirmDeckOperation` / remove | −1 конкретная копия; неизвестный/удалённый ID не затрагивает другую |
| replace | 0 по размеру; новый ID, уровень выбранного предложения, без наследования старого улучшения |
| upgrade | 0 по размеру; тот же ID, 0→1 один раз; по умолчанию недоступно, тестовый допуск изолирован |

Операции возвращают новое состояние и проверяют все условия до изменения состава/счётчика/расхода источника. Во время боя, незавершённой комнаты/награды и после финала сервисы запрещены. Выбор и отмена до подтверждения не посылают команду и не расходуют сохранённый источник. Решённые предложения записываются в `decisions`; услуги дополнительно сохраняют `resolved`. UI передаёт ID предложения/комнаты, поэтому старое событие не применится к следующей награде/привалу. Боевые результаты проверяют комнату и идентичности участников; ID боевых действий имеют новое пространство при перезапуске/новом бое.

## Сохранение и восстановление

`src/game/runSave.ts` отделяет JSON-контракт от транспорта через `SaveStorage`. Используется существующий `localStorage` браузера/WebView Tauri без новых зависимостей. Snapshot содержит готовую скрытую карту, маршрут, HP/maxHP и ID героев, колоду/счётчик/уровни, предметы/владельцев, текущее предложение, журнал расхода источников, `battleEntry`, конфигурацию экономики и revision.

Поддерживается **только схема 1** с точными `RULES_VERSION`, `GENERATOR_VERSION` и автоматическим fingerprint текущего каталога карт/предметов/ростера. Разрешены существующие игровые конфигурации A/B/U, обычная игра по-прежнему B. Неизвестные версии/ID/поля, включая незнакомые исполняемые эффекты, не принимаются. Проверяются структура, контрольная сумма, диапазоны здоровья/уровня, уникальность копий/владельцев, счётчики, маршрут и согласованность текущей фазы/предложения/решений. Ничего не удаляется и не «исправляется» при загрузке. Контрольная сумма обнаруживает случайное повреждение, криптографической защитой от редактирования она не является.

Snapshot записывается:

1. При создании похода.
2. После выбора комнаты, **до первого боевого действия**.
3. Сразу после определения победы/поражения движком, вместе с итоговым HP и наградой; ждать кнопки результата не нужно.
4. После принятия/пропуска/предмета/лечения и при завершении похода. Будущий UI услуг должен публиковать результат через тот же путь сохранения.

Пока бой не закончен, `run.heroes/deck/artifacts` остаются состоянием входа; `battleEntry` хранит комнату и независимый seed. Это компактный entry snapshot без второго списка карт/героев. Загрузка вызывает тот же `createCampaignBattle` с тем же противником, здоровьем, колодой, предметами и seed: рука/RNG воспроизводятся, бой начинается с хода 1. Pending/анимации не сериализуются. Карта/награда/незавершённый привал возобновляются точно; открытый просмотр колоды возвращается к той же награде. Завершённый поход позволяет только посмотреть итог или начать новый.

Основной ключ — `spellwhim.run.v1`, зеркало — `spellwhim.run.v1.backup`. Одна запись `setItem` атомарна и содержит весь snapshot. Сначала пишется основной ключ, затем зеркало того же подтверждённого состояния: повреждение одного ключа не возвращает уже взятую награду. До успешной основной записи зеркало сохраняет предыдущий рабочий snapshot. Загрузка проверяет оба ключа и выбирает наибольшую валидную revision; восстановление резервной копии сообщается игроку. Несовместимая версия блокирует автоматический откат к старой совместимой записи. Исходные записи при чтении не изменяются.

При ошибке записи/доступа/quota приложение явно сообщает об отсутствии надёжного сейва; доступны повторное сохранение того же состояния и скачивание JSON. Даже при успешной основной записи сбой зеркала считается ошибкой надёжности. Экспорт остаётся доступен из памяти при отказе хранилища. При сбое обоих записей прогресс нельзя гарантировать после закрытия; если сбой зеркала совпадёт с последующим повреждением основного ключа, возможен возврат к предыдущему целостному snapshot с предупреждением.

## Проверки

- `npm test`: **333 теста**, 22 файла; в том числе 45 новых тестов и 1 000 фиксированных последовательностей операций/сейва. Исторический контроль 427 боёв прошёл без перезаписи.
- `npm run build`: TypeScript/Vue и production-сборка. Сохраняется предупреждение Vite о крупном основном чанке.
- Compatibility smoke: `node scripts/run-combat-challenge.mjs --runs 3 --seed 42 --rosters A --strategies balanced,defensive,planner --policies safe,risky --artifacts real --no-archetypes` — 18 полных походов, завершены без ошибок. Это проверка совместимости лаборатории, не новый вывод о балансе ростера A.
- Браузер внутри Codex, изолированный локальный origin: 1280×720 и 1920×1080 — награда, модальный обзор, дубли/описание/закрытие. Проверены reload после боевого розыгрыша, победы до кнопки результата, открытой награды, карты после пропуска и принятия (+1 до 19 карт), незавершённого привала, лечения (+6 один раз) и терминального поражения до кнопки результата. Временный viewport override снят.
- Элита, оба исхода полного похода, backup, несовместимые версии, запись/quota/доступ и повторы покрыты автоматическими тестами. Полная ручная победа до босса, элитная замена слота и нативный Tauri в этой сессии не проверялись; ошибки storage проверялись инъекцией транспорта, без принудительной порчи браузерного профиля.

## Ограничения и следующий этап

Один текущий поход в одном origin/профиле, обычная одноконная игра; межоконная синхронизация, облако и UI импорта файла не добавлены. Схема пока описывает существующий генератор/ростер, никаких фиктивных будущих событий не сохраняет. Миграций из несуществовавшего сейва v0 нет; последующие миграции следует вводить в `decodeSnapshot` по версии схемы, сохраняя исходный JSON и проверяя результат перед публикацией. Изменения правил/генератора требуют явной версии, изменения данных отражаются fingerprint.

Для этапа 2 реализовать настоящий каталог в `resolveCardDefinition` и подключить его ко всем потребителям экземпляра (включая стоимость/preview/ботов и лаборатории). Сейчас resolver отклоняет уровень 1: приложение не показывает фиктивную силу и не запускает неподдержанный вариант в бой. Сохраняемость/получение уже улучшенной копии проверены изолированными fixtures; предложения боевой игры всегда уровня 0. При появлении каталога заменить тестовый допуск upgrade проверкой этого каталога, добавить сравнение старой/новой версии в UI и тесты preview=эффект. Постоянные ID, операции и `offer.cards: CardAcquisition[]` менять для этого не требуется. Золотую уникальность подключать в общем `validateAcquisition` с контекстом постоянной колоды вместе с настоящим каталогом золота.
