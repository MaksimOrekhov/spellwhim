# Status Foundation v0.1

Архитектурная версия **с нулевым изменением игрового баланса**. Игра, карты, враги, экономика, пять артефактов и вид интерфейса работают как раньше. Появилась общая основа для статусов (баффов, дебаффов, состояний героев и врага), родство карты с героем через состав отряда и единый набор правил расчёта урона. Новых статусов, карт и врагов нет: Кровотечение, Ослабление, Оглушение и Уязвимость героя в игру **не** добавлены.

Геймдизайнерская основа — [исследование Combat Status & Synergy System v1.0](design/combat-status-synergy-research-v1.md) (это предложения, а не правила; здесь реализован только фундамент).

## Что изменилось, одним взглядом

| Было | Стало |
|---|---|
| `enemy.vulnerable: boolean`, `consumeVulnerability`, `hasStatus` с проверкой одного ID | `BattleState.statuses` — единственное хранилище, `statuses.ts` — единственное описание правил |
| Бонус Ледяной стрелы/Грозового разряда: `damageBonus.hero: 'mage'`; подпись «броня Джайны» в UI | `damageBonus: { condition: 'owner-has-armor' }`; владельца даёт `party.ts` по классу карты |
| «Прикрыть союзника»: цель `'mage'` | цель `'class:mage'` через состав отряда |
| Формулы урона в `buildPlan`, `resolveCardPlay` и `forecastHit` по отдельности | `damage.ts` (`composeHit`, `splitDamage`) + единственный `damageEnemy` |
| Нет места для «срабатывает в момент хода» | `StatusDefinition.tick` + `runEnemyTurnStart` в `endTurn` |

## Архитектура

```text
src/game/
  statuses.ts   Определения и хранилище статусов: реестр, apply/consume/remove/cleanse/clear, модель для UI (statusViews)
  damage.ts     Единые правила удара: composeHit (список частей) и splitDamage (броня → здоровье)
  party.ts      Герой, связанный с картой/целью, через реальный состав отряда; формы имён для текста правил
  battle.ts     Применяет их: buildPlan, resolveCardPlay, forecastEnemyAction, endTurn, damageEnemy, runEnemyTurnStart
```

Правила по-прежнему только в `battle.ts` и вокруг него; Vue получает готовые данные.

### Определение статуса

`StatusDefinition` (в `statuses.ts`) отвечает на вопросы из постановки:

| Вопрос | Поле |
|---|---|
| ID, название, подписи | `id`, `name`, `shortName`, `description`, `note`, `spoken` (для скринридера по виду носителя) |
| Кто может нести | `carriers: ['enemy' \| 'hero']` — враг, герой, оба |
| Что значит число | `reading: 'charges' \| 'intensity'`, `maxValue` |
| Повторное наложение | `stacking: 'refresh' \| 'add'` |
| Срабатывание на ударе | `hitBonus` — плоский урон к следующему наносящему урон удару по носителю; удар тратит заряд |
| Срабатывание в момент хода | `tick: { phase, damage, ignoresArmor, decay }` |
| Данные для UI | `polarity`, `icon` (ключ, не разметка) |
| Удаление | `removeStatus`, `consumeStatus`, `cleanse(polarity)`, `clearStatuses`; при конце боя `updateResult` очищает всех носителей |

Три группы триггеров из исследования выражаются так (функция `triggerGroup`):

1. **Подходящая карта игрока** — `hitBonus` на враге: удар приходит от карты.
2. **Действие противника** — тот же `hitBonus` на герое: удар приходит от действия врага.
3. **Определённый момент хода** — `tick` с фазой (`enemy-turn-start`). Других фаз пока нет: добавлять их нужно вместе с реальным статусом, которому они нужны.

Шины событий на десятки видов нет намеренно: правило описывается данными, а движок вызывает его в точках, которые у боя уже есть.

### Как хранится Уязвимость

`state.statuses.enemy = [{ id: 'vulnerability', value: 1 }]`; у героев те же списки: `statuses.warrior`, `statuses.mage` (в игре пока пустые). Поля `enemy.vulnerable` **больше нет** — два источника истины невозможны, адаптеров совместимости не оставлено. Совместимость сохранена на уровне API: `hasStatus(state, 'vulnerability')` работает как раньше (второй необязательный аргумент — носитель), а `previewCard` по-прежнему отдаёт `vulnerabilityBonus`, `bonuses`, `appliedStatuses`. Тестам, которые писали `state.enemy.vulnerable`, дали `applyStatus` / `hasStatus`; их смысл не менялся.

Правила Уязвимости (не изменились, подтверждены регрессионной базой):

- накладывается на врага, не суммируется (`stacking: 'refresh'`, `maxValue: 1`), сохраняется между ходами;
- следующая карта с **фактическим** уроном получает +3 **до** брони; статус тратится даже при полном поглощении;
- карта без реального урона (в том числе неактивный условный урон) статус не тратит;
- карта, которая и расходует, и накладывает, сначала тратит старый заряд; новый остаётся, только если враг выжил;
- конец боя очищает статусы всех носителей.

Какие статусы тратит розыгрыш, решается на старте (`PendingPlay.consumedStatuses`), поэтому предпросмотр, план и исполнение видят одно и то же. Эффект карты `{ type: 'status', status, amount? }` накладывает статус по правилам определения (раньше любой статус превращался в Уязвимость — это закрыто).

### Герой, связанный с картой (`party.ts`)

Идентичности остаются раздельными: `characterId` (личность), `classId` (класс, решает, чья это классовая карта), `partySlot` (место в отряде, задаёт порядок), `instanceId` (участник похода, владелец артефакта). Ключи `warrior`/`mage` в `BattleState.heroes` — унаследованные ключи движка; **правила классовых условий их не используют**.

Контракт владельца классовой карты (`cardOwner` / `heroForClass`):

- владелец — участник отряда, чей `classId` равен `className` карты;
- один подходящий участник → владелец; никого → `absent`; несколько (два героя одного класса) → `ambiguous`;
- `absent` и `ambiguous` означают «правило не применяется»: герой **не выбирается молча** (бонус от брони не срабатывает, адресная броня никому не выдаётся, анимация берёт название класса, а не имя);
- у физических копий карт владельца нет — он не нужен текущим правилам.

Что переведено:

- `damageBonus: { condition: 'owner-has-armor', amount }` (раньше `hero: 'mage'`);
- адресная защита `target: 'class:mage'` («Прикрыть союзника»); `threatened`, `partner` и прямые ключи героев работают как раньше, `partnerOf` берётся из состава отряда;
- порядок областей атак, `threatened` и стартовый фокус — по слотам, а не по литералам `['warrior', 'mage']`;
- подпись бонуса («броня Джайны») берёт форму имени по `characterId` (временная таблица `characterForms`, неизвестный персонаж → «героя»); подпись источника анимации — через владельца карты.

**Ограничения.** Пара из двух героев одного класса не разрешается автоматически (см. выше). Бот Balance Lab (`balance.ts:215`) всё ещё выбирает вес по `className === 'warrior'` — это эвристика бота, а не правило игры.

### Расчёт урона (`damage.ts`)

Удар — упорядоченный список частей `HitPart` (`base`, `class-bonus`, `status`, `artifact`; уменьшения — отрицательные части). `composeHit` суммирует по порядку и не даёт итогу уйти ниже нуля, записывая уменьшение как фактически снятое. Порядок: база → условие класса → статусы → артефакты → уменьшения. (Исследование предлагало «статусы → класс»; выбран порядок, в котором строки уже показывались в UI, на сумму он не влияет.) `splitDamage` — единственное место, где броня поглощает урон.

Кто что использует:

| Место | Что делает |
|---|---|
| `buildPlan` (предпросмотр и план карты) | собирает части: база, условие владельца, `hitBonuses(enemy)`, артефакты → `composeHit` → `splitDamage`; кладёт части в `CardPreview.damageParts` |
| `resolveCardPlay` | снимает потраченные статусы, наносит **уже собранный** итог через `damageEnemy` |
| `damageEnemy` | единственная точка, где враг теряет броню и здоровье, включает порог второй фазы; общая для карты и будущих тиков |
| `forecastEnemyAction` / `forecastHit` | собирает части удара по каждому герою (`hitBonuses(герой)`, расклин), `composeHit`, `splitDamage`; в прогнозе есть `parts` и `consumedStatuses` |
| `endTurn` | исполняет **тот же** прогноз: потеря здоровья берётся из него, потраченные статусы героев снимаются по нему |

Поэтому намерение и результат совпадают по построению. UI (`cardDisplay.damageParts`) только переводит части движка в подписи.

**Более узкое решение вместо одной гигантской функции.** Урон карты по-прежнему сводится в один удар, а расчёт урона по врагу и по героям идёт в двух функциях, различающихся только сбором модификаторов; арифметика одна. Объединять их глубже не стали: карты и атаки врага различаются (броня врага убывает на поглощённое, броня героя после удара обнуляется), и общий «универсальный удар» потребовал бы условий на каждом шаге.

### Где подключаются артефакты

Логика пяти артефактов осталась на своих местах и срабатывает в тех же моментах (один раз, по тем же условиям): добавлены только источники данных.

- «Линза слабой точки» читает `consumedStatuses` плана (раньше — `vulnerabilityBonus > 0`);
- «Верный расклин» — часть удара с отрицательной суммой в `forecastHit`; `artifactReduction` считается из неё;
- «Натяжной шкив» — артефактная часть в `buildPlan`; остальные два не менялись.

Повторных вызовов не появилось: статусный слой не вызывает артефакты, а артефакты не вызывают статусный слой. Тест «Weakpoint Lens» проверяет единственное срабатывание на потраченную Уязвимость и один раз за бой. Остаётся как есть: триггеры артефактов сопоставляются по строке причины (`reason`) — унаследованная особенность Artifact Foundation, вне этой задачи.

### Куда подключатся будущие эффекты

| Эффект | Точка |
|---|---|
| Кровотечение | определение с `tick` в `statuses.ts`; ход: `endTurn → runEnemyTurnStart → damageEnemy → фаза/победа → действие врага` (см. пример) |
| Ослабление | часть удара с отрицательной суммой в `forecastHit` (рядом с расклином) и трата через `consumedStatuses` |
| Уязвимость героя | **уже работает в движке**: `hitBonuses(герой)` в `forecastHit`, трата при исполнении; нужно лишь, чтобы действие врага её накладывало |
| Оглушение | новая ветка в `endTurn` перед исполнением действия (пропуск действия) — потребует решения Q6 исследования |
| Снятие негативных | `cleanse(state, carrier)` уже есть как функция; нужен эффект карты |

## Пример: как будет добавляться Кровотечение

Это пример использования архитектуры, а не готовая игровая реализация. Проверен тестами-фикстурами (`statusFoundation.test.ts`, блок «where future statuses plug into the turn»), в игру не включён.

1. **ID** — `types.ts`: `export type StatusId = 'vulnerability' | 'bleed'`.
2. **Определение** — `statuses.ts`, запись в `statusDefinitions`:

```ts
bleed: {
  id: 'bleed', name: 'Кровотечение', shortName: 'Кровь',
  description: 'В начале хода врага теряет здоровье, равное силе, затем сила уменьшается на 1. Броня не поглощает.',
  spoken: { enemy: 'Противник истекает кровью', hero: 'Герой истекает кровью' },
  polarity: 'negative', carriers: ['enemy'], reading: 'intensity', stacking: 'add', maxValue: 6,
  tick: { phase: 'enemy-turn-start', damage: true, ignoresArmor: true, decay: 1 },
  icon: 'bleed',
},
```

3. **Иконка** — добавить ключ `'bleed'` в `StatusIconKey` и сопоставление в `HeroPortrait.vue` (Lucide `Droplet`, без собственной SVG).
4. **Карта** — данные в `types.ts`: `{ type: 'status', status: 'bleed', amount: 2 }`.
5. **Остальное готово:** `buildPlan`/`resolveCardPlay` применяют статус, `endTurn` тикает его до действия врага через общий `damageEnemy` (поэтому смерть и переход во вторую фазу согласованы с обычным уроном), `cloneBattleState` и ключи дедупликации планировщика уже учитывают все статусы, `statusViews` отдаёт его UI.
6. **Что придётся сделать руками:** текст/метки карты (`cardTags` и ключевые слова в `cardDisplay.ts` пока знают только Уязвимость), вес карты в эвристиках Balance Lab, арт, тесты и симуляции, а решение об ограничении силы и о защите врагов — отдельное игровое решение.

## Что осталось нереализованным

- Конкретные статусы: Кровотечение, Ослабление, Оглушение, Уязвимость героя в игровом процессе, очистка.
- Действия врагов, накладывающие статусы (`afflict`, `cleanse`, `empower`).
- Тики героев и фазы, кроме `enemy-turn-start`; прогноз «что произойдёт в конце хода» в интерфейсе.
- Общая шина боевых событий и вывод артефактных триггеров из неё.
- Многоударные карты и «только первый удар получает бонус».
- Обобщение UI: подсказки и теги карт под любой статус; панель нескольких статусов (`HeroPortrait` уже принимает список).
- Два героя одного класса; роли Party System за пределами `warrior`/`mage`.
- Решения Q2 (лечение), Q6 (оглушение), Q7 (предел брони героя) из исследования.

### Производительность планировщика

Стоимость измерялась на одной машине попеременно со старым деревом (внутрипроцессный бенчмарк, 150 полных походов `planner`). Число узлов поиска не изменилось (в среднем 45 узлов на ход).

| | мс на поход |
|---|---|
| до | 2,2 |
| после | 2,6–2,7 (примерно +20%) |

Первая версия давала примерно +70%; ускорили горячие пути (порядок слотов без сортировки для двух героев, поиск владельца без аллокаций, быстрые ветки при пустых статусах, ленивый расчёт данных только для UI). Типичные симуляции остаются практичными: 200 походов планировщика ≈ полсекунды.

## Архитектурные компромиссы

- **Статусы вне `Hero`.** Хранилище лежит в состоянии боя, а не в объектах героев: герои переходят между боями через `previousHeroes`, и статусы не должны попасть в поход. Цена: второй список вместе с `heroes`.
- **Уязвимость героя уже работает в движке, но не включена в игре.** Это следствие общего правила `hitBonus`, а не отдельная ветка. Включение остаётся решением геймдизайна.
- **Данные вместо шины событий.** Тик описывается данными и вызывается из одной точки. Если потребуется сложнее (реакции артефактов на статусы), событийный слой добавляется поверх, а не заранее.
- **`bonuses`/`vulnerabilityBonus` в `CardPreview` сохранены ради UI и тестов**, хотя новые потребители должны использовать `damageParts`.
- **Тестовые определения статусов.** Тесты регистрируют временные определения прямо в таблице `statusDefinitions` (через приведение типа) и убирают их в `finally`. Это допустимо для фикстур; в игровом коде таблица не изменяется.
- **Первая версия порядка модификаторов** отличается от предложенного в исследовании (см. выше); решение отражено в комментариях `damage.ts` и `types.ts`.

## Расхождения с исследованием

- Исследование проводилось до Artifact Foundation. После внедрения артефактов правило «нельзя проектировать в отрыве от триггеров» учтено: фундамент отдаёт им `consumedStatuses` и части удара, но не переписывает их.
- Q1 (владелец карты) решён технически как «вывод по классу через состав отряда с контрактом на неоднозначность»; рекомендация исследования «в состояние не хранить» выполнена.
- Q10 (миграция `vulnerable`) выполнена полностью, без временных адаптеров.
- Расхождение backlog ↔ код (`CardLink`) по-прежнему требует отдельной сверки: в коде такого типа нет.
- Рекомендация исследования ввести «события» (W9) сознательно сужена до `consumedStatuses` и данных тика: большая шина избыточна для единственного статуса.
